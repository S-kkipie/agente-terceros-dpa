Guion de demo: Agente de Terceros (DPAs)

2.ª entrega del TIF · máximo 15 minutos · lo presenta un integrante elegido al azar, así que los tres deben poder seguir este guion.

1. Antes de la clase (la noche anterior y 15 min antes)

  • Clonar o actualizar el repo e instalar: uv sync
  • Ollama corriendo y con el modelo de embeddings: ollama serve · ollama pull nomic-embed-text
  • .env con OPENROUTER_API_KEY (y GOOGLE_API_KEY como respaldo)
  • Todo en verde: 
    uv run agente-terceros diagnostico
  • Datos de demostración (si la base está vacía): uv run agente-terceros demo
  • Calentar la caché: revisar una vez los tres contratos de ejemplo; en la clase saldrán al instante y gratis: 
    for f in data/ejemplos/*.txt; do uv run agente-terceros revisar "$f" -o /tmp/x.md; done
  • Levantar la interfaz y abrir http://localhost:5000: uv run agente-terceros web
  • Dejar abiertos: el navegador (Panel), una terminal en el repo y la hoja de entrega o las diapositivas
Plan B
  • Si OpenRouter falla (sin saldo, 429), el agente pasa solo a Gemini y luego a Ollama; el pie de la página muestra qué proveedor respondió.
  • Si no hay internet: los contratos de ejemplo salen de la caché; para lo demás, TERCEROS_LLM_PROVIDER=ollama uv run agente-terceros web (más lento).
  • Si se cae todo: mostrar los informes ya generados en data/salidas/ y las capturas de las diapositivas.

2. Guion minuto a minuto

  1. 0:00–1:30
    Problema y objetivo. Los encargados (nube, planillas, pagos) tratan datos por nosotros y la responsabilidad sigue siendo nuestra. Revisar DPAs a mano es lento. Nuestro agente es el A7 de los 8 del PIMS ISO/IEC 27701:2025.
    Mostrar la hoja de entrega: nombre, integrantes.
  2. 1:30–3:00
    Arquitectura y controles. Interfaz web y orquestador → agente con herramientas MCP → revisor, riesgo, repositorio; FAISS y Ollama locales; proveedor de IA intercambiable. Controles A.1.2.7 y A.2.5.7–A.2.5.9; LPDP art. 30; RLPDP arts. 28-33 y 36.
    Diagrama de la hoja.
  3. 3:00–4:30
    Panel. 4 encargados, 2 de riesgo crítico, 1 sin DPA, alerta de renovación (PagoFácil, próximo a vencer), decisiones pendientes.
    Pestaña Panel → Proveedores → abrir MailRápido: riesgo 12/16 y sus factores.
  4. 4:30–7:30
    Revisar un DPA en vivo. Revisar DPA → proveedor LabClínico → subir data/ejemplos/dpa_pagofacil_intermedio.txt → mostrar el %, las cláusulas que faltan, una cita literal y su fundamento (fuente, artículo, página).
    Decir: "si el modelo no puede citar literal el contrato, no lo damos por cumplido".
  5. 7:30–8:30
    Aprobación humana. Aprobaciones → rechazar el DPA de MailRápido con un comentario → Bitácora: queda registrado quién decidió y cuándo.
  6. 8:30–11:00
    Orquestación multiagente (MCP). En la terminal: 
    uv run agente-terceros orquestar brecha --categoria salud
    El Agente de Incidentes llama por MCP a processors_in_breach, check_dpa_status y evaluate_vendor; prioriza y deja la notificación (48 h, RLPDP art. 34) al DPO. Mostrar también la pestaña Brecha.
  7. 11:00–12:30
    Skill y asistente. Abrir skills/revisar-dpa/SKILL.md (descripción de activación y pasos) y asistente/ (identidad, instrucciones, conocimiento). Ejecutar la skill: 
    uv run agente-terceros revisar data/ejemplos/dpa_mailrapido_deficiente.txt
  8. 12:30–13:30
    Consulta normativa. "¿En qué plazo debe el encargado notificar un incidente en el Perú?" → respuesta con citas [RLPDP, art. 36].
  9. 13:30–15:00
    Resultados y cierre. Exactitud por cláusula 87,2 %, cumple/no cumple 92,3 %, 98,9 % de citas verificadas; cobertura de norma peruana de 15 % a 69 %. Limitaciones: evaluación pequeña, numeración ISO inferida, sin OCR.

3. Preguntas probables

¿Y si el modelo inventa?Cada cita se verifica literal contra el contrato; si no aparece, la cláusula no cuenta como cumplida y se marca para revisión. Además, ningún resultado surte efecto sin aprobación humana.
¿Por qué no indexaron la ISO/IEC 27701?No es de libre acceso. Catalogamos los títulos de los controles con una paráfrasis propia; la numeración de 2025 se infiere de la edición 2019 (Anexo F).
¿Salen datos personales a la nube?Los embeddings y la búsqueda son locales (Ollama + FAISS). Al LLM solo va el texto del contrato y fragmentos públicos de la norma, nunca la base de datos personales. Con TERCEROS_LLM_PROVIDER=ollama todo queda local.
¿Por qué OpenRouter / Gemini?OpenRouter permite cambiar de modelo sin tocar el código; Gemini 2.5 Flash es rápido y barato (≈ US$ 0,01 por revisión). El agente acepta Gemini directo, OpenAI o compatibles, Anthropic u Ollama, con respaldo automático.
¿Cómo se integra con los otros 7 agentes?Por el bus MCP: el servidor pims-terceros expone sus herramientas por JSON-RPC (stdio); el flujo de brecha muestra al Agente de Incidentes usándolas.
¿Por qué SQLite y no PostgreSQL?Para la demo en PC; el esquema usa tipos portables y la migración a la base PostgreSQL central del PIMS es directa.
Regla de oro: si algo tarda, explicar mientras carga lo que está haciendo (recupera normas por cláusula, una sola llamada al modelo, verifica citas). Una revisión toma unos 10-15 s; de caché, instantánea.
